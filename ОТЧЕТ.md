# Отчёт: непрерывное интеграционное тестирование (CI)

## 1. Проект

Используется проект «Магазин» из задания 7 (товары и заказы; Java 21, Spring Boot 4.1, Maven).
В нём 13 интеграционных тестов (нисходящие, восходящие, сходящиеся), они запускаются командой `mvn test`
и используют H2, поэтому в CI не нужна внешняя база данных.

## 2. Настройка конвейера

Инструмент: **GitHub Actions**. Конвейер описан в файле `.github/workflows/ci.yml`.

**Когда запускается:**
- `push` в любую ветку;
- `pull_request`;
- вручную, кнопкой *Run workflow* (`workflow_dispatch`).

**Шаги (job `test`, машина `ubuntu-latest`):**

| Шаг | Что делает |
|---|---|
| 1. Скачать код | `actions/checkout@v4` |
| 2. Установить Java 21 | `actions/setup-java@v4` (Temurin 21, кэш Maven) |
| 3. Запустить тесты | `mvn -B test` — если хоть один тест упал, шаг и весь запуск становятся красными |
| 4. Сохранить отчёты | `actions/upload-artifact@v4`: папка `target/surefire-reports` (выполняется всегда) |
| 5. Итог в сводку | строки «Tests run…» выводятся на странице запуска (Summary) |

**Схема:**

```
 git push ──> GitHub ──> Actions: checkout -> Java 21 -> mvn test -> отчёты
                                                     │
                                ┌────────────────────┴──────────────────┐
                           все тесты прошли                    тест упал
                           ✅ зелёная галочка              ❌ красный крестик + письмо автору
```

## 3. Проверка работы конвейера (что сделать и куда вставить скриншоты)

Порядок действий описан в README_ЗАЩИТА.txt, раздел 3. В отчёт нужно вставить результаты своего репозитория.

| # | Изменение | Ожидаемый результат | Фактический результат |
|---|---|---|---|
| 1 | Первый push проекта | ✅ зелёный, `Tests run: 13, Failures: 0` | *(скриншот вкладки Actions)* |
| 2 | Коммит с ошибкой: в `OrderService` убрана проверка остатка | ❌ красный, упали TD-3, BU-3, CV-2 | *(скриншот упавшего запуска)* |
| 3 | Коммит-исправление (проверка возвращена) | ✅ снова зелёный | *(скриншот)* |

Ссылка на репозиторий: `https://github.com/<логин>/task8-ci-cd`

**Проверено локально (та же команда, что в конвейере, `mvn -B test`):**

```

[INFO] Tests run: 3, Failures: 0, Errors: 0, Skipped: 0 -- in ru.study.shop.OrderConvergedIT
[INFO] Tests run: 5, Failures: 0, Errors: 0, Skipped: 0 -- in ru.study.shop.OrderTopDownIT
```

При внесённой ошибке №2 (проверка остатка убрана) тот же запуск дал
`Tests run: 13, Failures: 2, Errors: 1` (упали TD-3, BU-3, CV-2) и BUILD FAILURE.
В GitHub Actions это даёт красный запуск.

## 4. Результаты и выводы

1. Настроен конвейер CI: тесты запускаются **автоматически при каждом изменении** кода, человек
   в этом не участвует.
2. Конвейер **фиксирует результат**: статус коммита (✅/❌), лог каждого шага, сводку тестов,
   скачиваемый архив отчётов `test-reports`.
3. Ошибка, внесённая в код, сразу видна по красному статусу. Сломанный код не останется незамеченным,
   а с защитой ветки (*Branch protection → Require status checks*) его нельзя слить в main.
4. Плюсы CI: тесты гоняются всегда, одинаково и в чистом окружении («у меня работает» не пройдёт),
   ошибка находится через минуты после коммита.
5. Возможные доработки: прогон на реальной PostgreSQL (service-контейнер в Actions), отчёт о покрытии
   кода (JaCoCo), автоматический деплой (CD) после зелёных тестов.
